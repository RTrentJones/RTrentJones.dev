> Greenlight is a deployment and verification framework for small projects. From one manifest
> entry per tool it emits Terraform for pluggable providers (Cloudflare Workers, Vercel, Oracle
> Cloud, a Docker host, Neon and Supabase) and runs a strict **deploy → verify → promote** loop. Six
> verification modes, combinable per tool, decide whether a deploy is good, and promotion only
> advances the exact commit that passed. Every project on this site ships through it, including the
> blog you're reading.

Part of my work at Amazon, on Alexa, was developer tooling and the machinery that ships software:
environments, deploys, and the checks that decide whether a build is fit to promote. Greenlight is a
small, personal version of that kind of system. I built it while reviving HeistMind, after noticing that I had rebuilt the
same deploy-and-check loop for several side projects; [the story is in a
post](/blog/greenlight/).

Most personal infrastructure decays once you stop looking at it. Free-tier databases pause, a
dependency drifts, a "live" link starts returning 404, and you find out months later. Greenlight
treats "deployed and working" as something each push has to demonstrate. The same harness that
deploys a tool also verifies it, and the same code runs on my laptop, in CI and for an agent, so a
local check and the production gate mean the same thing.

## Six verify modes, and what each one shows

A tool declares how it must be verified, and the harness runs one `verify(baseUrl, spec)` with the
modes that fit, combinable as a list. Each mode answers a different question:

- **`api`.** Does the deployed surface respond correctly? HTTP status and body checks. For this
  blog that means every route returns 200, the RSS feed and sitemap parse, and no internal link is
  broken.
- **`playwright`.** Do the real UI flows work in a browser, including signed-in ones?
- **`test`.** Does the tool's own suite pass against what's about to ship? CI won't deploy a tool
  whose tests are red.
- **`mcp`.** Does an MCP server speak the protocol? It runs `initialize`, lists the tools, calls
  one and checks the response, and checks that an unauthenticated call is rejected. The tool list
  has to match exactly, so a dropped or renamed tool fails the deploy.
- **`eval`.** Are an MCP server's answers good? A model grades its responses against a rubric, so
  quality regressions show up alongside crashes.
- **`agent-web`.** Can an agent complete a real task? A model drives a live browser through a
  scenario and the result is scored.

The number matters less than the fit. Verification means something specific to each kind of tool:
an HTTP check for a static site, a protocol handshake for an MCP server, a graded answer for a tool
whose output is a judgement.

## Releasing exactly what was verified

Branches map to environments: **`develop` → beta** and **`main` → prod**. Pull requests are checked
locally with `greenlight preview`, which builds the tool, serves it and runs the same verification.
A release is one `greenlight ship`: build, deploy, verify that the deployed `/__version` reports the
commit that was just shipped, and roll back if verification fails.

Promotion is an explicit, gated fast-forward, pinned to a single commit from start to finish:

1. Record `develop`'s tip commit.
2. Verify beta, including that it is serving that exact commit.
3. Fast-forward `main` to that commit and no further, so commits that landed on `develop` after the
   verification don't ride along.
4. Ship prod at that commit and verify it, rolling back on failure.

Deploys skip cleanly when cloud credentials are missing, but promotion doesn't. A missing credential
can skip an action, never a check, so a promote without what it needs to verify fails loudly.

## Infrastructure as emitted code

The manifest is the single source of truth. `greenlight add <name> --lane <l> --target <t>`
scaffolds a tool, appends one entry describing what it is, where it runs and how it is verified, and
emits a Terraform file for it that uses Greenlight's shared modules, pinned to the same version as the
npm package. The CLI edits the infrastructure code; CI applies it. For the common combinations, a
new target or data store is a manifest change. Anything unusual can still be written by hand beside
the generated files.

## Liveness

Some things go quiet when nobody uses them. A Supabase database pauses after a week without database
activity, so a Cloudflare Worker on a cron is meant to query a real table often enough to keep it
awake. An
Oracle Cloud free-tier container can be reclaimed, so the same Worker probes it and, for tools that
opt in, fires a `repository_dispatch` that re-applies the infrastructure, redeploys and re-verifies.
Neon suspends itself between uses and wakes on the next connection, so it is deliberately left
alone. A failed probe opens a GitHub issue.

The keepalive has failed in instructive ways, once by reporting a database healthy while it paused,
and the details are in [a post of their own](/blog/keepalive-green-database-paused/).

## What it has caught

Checking the deployed commit is the part that has paid for itself most clearly. When Polyphony
reworked its API in July, its verify spec still probed an endpoint that no longer existed, and yet
deploys had been passing. The earlier passes had been checking the old container, which was still
serving traffic after the deploy. Once verify had to confirm the deployed `/__version`, it checked
the new image, the stale probe failed, and the gap became visible.

## A few design choices

- **Checks are enforced on every push.** Each push re-runs a tool's declared verification, in the
  mode that fits it, instead of trusting the last green run.
- **One harness, many providers.** The same loop ships an Astro site to Workers, a Next.js app to
  Vercel, and Python services to Oracle Cloud containers. Lane and target are manifest fields, and
  the discipline doesn't change between them.
- **Published and consumed at arm's length.** Greenlight ships to npm as
  [`@rtrentjones/greenlight`](https://www.npmjs.com/package/@rtrentjones/greenlight). This site is a
  thin consumer pinned to a release, so framework changes arrive as a version bump, never as
  copied-in source.
